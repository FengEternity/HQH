# 分支与发布

## 长期分支

| 分支 | 用途 |
| --- | --- |
| `main` | 发布与验证。只放准备上传体验版/正式版、或已经过验证的代码。不在这条分支上直接 commit；发行版缺陷走下面的 `hotfix-*`。 |
| `dev` | 研发集成。已验收的功能从短分支合入这里，做联调与回归。不要在 `dev` 上直接堆未完成的大功能。 |

## 功能短分支（从 `dev` 迁出）

下一期按模块**逐渐**开发：每次从当前 `dev` 拉一条短分支，**一条分支只做一件可验收的事**，做完合回 `dev`，再拉下一条。不要直接从 `main` 拉功能分支。

命名：`dev-<功能>`，全小写，单词用连字符。

与实现计划对应的例子：

| 短分支 | 对应计划 |
| --- | --- |
| `dev-tabbar-shell` | 底栏四 tab 壳层 |
| `dev-shop-catalog` | 可售商品与视频关联 |
| `dev-cart-pay` | 购物车、支付、订单 |
| `dev-ai-search` | 统一 AI 搜索 |
| `dev-player-agent` | 播放页文档问答（pi-agent-core） |
| `dev-cs-agent` | 客服 AI 与转人工 |

其它小修同样用 `dev-<简述>`，不要用 `feat/` 前缀。

## 发行版热修（从 `main` 迁出）

线上/体验版已发布代码上的缺陷，从当前 **`main`** 拉热修短分支，**不要**从 `dev` 拉（`dev` 上可能已有未发布改动）。一条分支只修一件可验证的事，验证后合回 **`main`**，再用于微信侧重新上传。

命名：`hotfix-<简述>`，全小写，单词用连字符。例如 `hotfix-pay-callback`。

1. 确认在最新 `main`：`git checkout main` 并 `git pull`（已跟踪远程时）。
2. 迁出热修分支：`git checkout -b hotfix-<简述>`。
3. 只在该短分支上改、提交、自测；用 `main` 对应的发布路径验证（体验版/真机，不要拿未合入 `main` 的 `dev` 代码当发行版验证）。
4. 验证通过后：**合并回 `main`**（PR 或快进），在 `main` 上上传/发版。合入后可删本地热修分支。
5. 同一提交也要合入（或 cherry-pick 到）**`dev`**，避免后续 `dev` → `main` 时把热修冲掉或漏带。

未上线的功能缺陷仍走 `dev-<功能>` → `dev`，不要用 `hotfix-*`。

## 工作方式

1. 确认在最新 `dev`：`git checkout dev` 并 `git pull`（已跟踪远程时）。
2. 迁出功能分支：`git checkout -b dev-ai-search`（名称换成上表对应项）。
3. 只在该短分支上开发、提交、自测。
4. 该功能验收后：**合并回 `dev`**（PR 或快进），不要直接合进 `main`。合入后可删本地短分支。
5. `dev` 上多块功能联调通过、准备发体验版/正式版时，再把 `dev` 合入 `main`，在 `main` 上用微信开发者工具上传、提交审核。
6. 发布后继续开发：回到 `dev`，再迁出下一条 `dev-<功能>`。发行版出了缺陷：按上一节从 `main` 迁出 `hotfix-*`，不要在 `main` 上直接改。

## 禁止

- 在 `main` 上直接 `commit`（功能走 `dev-<功能>` → `dev`；发行版缺陷走 `hotfix-*` → `main`）。
- 在 `dev` 上同时堆多个未验收大功能（应拆到各自的 `dev-<功能>`）。
- 把功能短分支直接合进 `main`，跳过 `dev`。
- 把 `hotfix-*` 当功能分支用，或从 `dev` 迁出 `hotfix-*`。
- 把未验证的云函数、支付、密钥相关改动推到 `main` 当日常备份。
- Force push `main`。

微信侧：上传体验版应对准 `main` 的已验证提交；日常预览可用当前 `dev-<功能>` 或 `dev` 本地编译，不要把未合入 `main` 的提交当成「已发布」。
