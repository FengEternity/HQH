# 关于页：版本号与更新日志

日期：2026-09-09  
载体：现有微信小程序（本仓库 `miniprogram/`）  
范围：用户端「我的」与运营后台首页各一个入口，共用一页、一份随包数据模块。不接云、不改发版流水线脚本。

## 背景与决策

小程序内没有任何版本展示，也没有 changelog。排障时用户和运营都说不清当前包是哪一版。微信 `wx.getAccountInfoSync().miniProgram.version` 只在正式版可靠；开发版 / 体验版经常为空，只能依赖 `envVersion`。

对话中已确认：

- 用户和运营都要能看（用户精简，运营完整）。
- 日志随仓库发版，不做成云端 CMS。
- 页面以包内版本为主，旁标环境；微信后台版本号只在运营路径展示（正式版才有值）。

## 目标

用户能从「我的」打开关于页，看到包内版本、环境，以及面向用户的更新说明，并能一键复制一行诊断文案。运营从后台打开同一页，额外看到内部备注和微信版本（或降级说明）。

## 非目标

- 云数据库 / 后台在线编辑 changelog
- 更新红点、强制更新、调用微信「检查更新」
- 自动把包内版本写进微信开发者工具上传表单
- 完善「我的」的登录、订单（本功能只加「关于」入口）
- 独立的用户关于页与运营诊断页（共用一页）

## 数据

单一事实源：`miniprogram/data/appRelease.js`，随小程序打包，页面 `require` 读取。无网络、无云函数。

写成 js 模块而不是 `.json`：小程序的 `require` 会给路径补 `.js`，直接 require JSON 会报 `module ... is not defined`，加载该模块的页面全部白屏。

```js
module.exports = {
  version: '0.3.0',
  releases: [
    {
      version: '0.3.0',
      date: '2026-09-09',
      user: ['面向用户的一条说明'],
      internal: ['仅运营可见的备注'],
    },
  ],
};
```

约定：

- `version`：当前包内版本，页面主展示用。与微信上传时填写的版本号尽量保持相同，但不做机器校验。
- `releases`：新版本在前。`date` 为日历日 `YYYY-MM-DD`。
- `user`、`internal`：字符串数组；可空或缺省（视为空数组）。
- 实现时用一份小模块规范化数据：缺失、非对象、`version` 非字符串时，页面主版本文案为「未知」，列表按空处理，不白屏。
- 首包内容：`version` 与当时产品状态一致；不必回溯全部历史。只写用户能感知的现状和本条功能本身；内部备注可写「关于页上线」一类。

运行时只读 `wx.getAccountInfoSync()`：

| 字段 | 展示 |
| --- | --- |
| `miniProgram.envVersion` | `develop` → 开发版；`trial` → 体验版；`release` → 正式版；其它 → 未知环境 |
| `miniProgram.version` | 非空才显示「微信版本 {version}」；空则仅 staff 路径显示「微信后台版本号仅正式版可见」 |

## 可见性

页面路径：`pages/about/about`。查询参数 `staff=1` 表示运营路径。

| 路径 | 鉴权 | 日志 | 微信版本行 |
| --- | --- | --- | --- |
| 无 `staff` 或 `staff` 不是 `1` | 无 | 只列出 `user` 至少一条的 `releases` 项；只渲染 `user` | 不展示（即使用户设备上是正式版，也不强调微信后台号，避免干扰） |
| `staff=1` | 与其它后台页相同：无 `hqh_admin_ticket` 则 `redirectTo` `/pages/admin/login/login` | 列出全部 `releases`；`user` 与 `internal` 都渲染，`internal` 使用次要样式 | 展示：有微信版本则显示号；否则显示降级句 |

用户路径即使本地已有运营 ticket，也不渲染 `internal`，保证运营从「我的」点进去时与用户所见一致。

用户路径筛完后一条都没有：展示「暂无面向用户的更新说明」，不要空白列表。

## 入口与页面

不进 tabBar。导航栏标题：关于。

**「我的」**（`pages/mine/mine`）

- 保留现有空态文案「登录后可查看订单」。
- 增加一行「关于」，右侧展示当前包内版本（未知则显示「未知」）。
- `navigateTo` `/pages/about/about`（不带 `staff`）。

**后台首页**（`pages/admin/home/home`）

- 在现有工作块之后增加「版本与日志」。
- 副文案：环境标签 + 包内版本。
- `navigateTo` `/pages/about/about?staff=1`。

**关于页自上而下**

1. 产品名：优度 · 仪器讲解
2. 主版本：`version` + 环境标签
3. 仅 staff：微信版本行（见上表）
4. 「更新说明」：每条为版本号、日期、条目列表
5. 点击主版本区域：`wx.setClipboardData`，成功 toast「已复制」。内容格式：
   - 默认：`优度 {version} · {环境}`
   - 仅 staff 且微信版本非空时追加：` · 微信 {wxVersion}`
   - `{version}` 在数据损坏时用「未知」
6. 复制失败：toast「复制失败」，页面仍可浏览

列表直接滚动，不分页、不折叠历史版本。

样式跟现有 `.page` / `.muted` / 后台 `hub-item` 一类全局样式，不引入新设计系统。

## 发版（人工）

细则以 `docs/versioning.md` 为准：默认升修订号，用户可感知的新能力再升次版本；正式上线前禁止 `1.0.0`。

准备把代码合入 `main` 并上传体验版 / 正式版前：

1. 若本轮有用户或运营需要知道的变化，按上述规则改 `appRelease.js` 的 `version`，并在 `releases` 头部追加一条。
2. 微信开发者工具上传时填写的版本号与 `version` 保持一致。
3. 纯热修若无需用户感知，可只写 `internal`、`user` 留空；该条不会出现在用户关于页。

不在本功能里加 CI 或上传钩子。

## 测试要点

- 开发者工具预览，用户路径：包内版本 +「开发版」；列表无 `internal`；仅 `internal` 的版本不出现。
- 同包 `staff=1` 且已登录运营：可见 `internal`、环境、微信版本降级句。
- `staff=1` 无 ticket：进入登录页。
- 数据损坏：主版本「未知」，用户路径空态文案，不白屏。
- 点击主版本：剪贴板含包内版本和环境。

## 实现边界

改动限于：上述数据模块、读取模块、关于页四件套、`app.json` 注册、`mine` 入口、`admin/home` 入口及对应极少量样式。不改云函数。
