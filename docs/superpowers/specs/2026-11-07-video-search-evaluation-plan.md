# HQH 视频搜索系统架构对比评测方案

> 文档路径：`docs/superpowers/specs/2026-11-07-video-search-evaluation-plan.md`  
> 文档日期：2026-11-07  
> 文档状态：评测方案设计  
> 适用模块：视频搜索（Keyword Retrieval / Vector Retrieval / LLM Retrieval / Reranker）

## 一、项目背景

### 1.1 当前搜索系统现状

HQH 项目目前已经实现基于关键词检索和向量检索的混合搜索能力。

其中：

- **关键词检索（Keyword Retrieval）**：基于视频预先构建的 `searchBlob`，通过文本规范化、同义词替换和字符串包含匹配查找视频。
- **向量检索（Vector Retrieval）**：通过 Embedding 模型将用户查询转换为向量，与视频知识库中的向量计算余弦相似度，完成语义召回。

现有混合检索在实际测试中存在以下问题：

1. 关键词检索能够完成基本的精确匹配，但对自然语言表达和语义差异较大的查询支持有限。
2. 向量检索使用固定相似度阈值进行过滤，阈值设置不合理时容易出现召回不足，或者引入少量不相关结果。
3. 不同检索路径的召回结果缺少统一的相关性排序机制，难以保证最终展示结果的准确性。

因此，项目计划探索引入 LLM 主动检索和 Reranker 重排序能力，改善视频搜索的召回覆盖率和排序质量。

### 1.2 评测目的

本次评测不以单独验证某一种检索算法为目标，而是从完整搜索链路出发，对不同搜索架构进行对比。

重点回答以下问题：

1. LLM 主动检索能否有效补充关键词和向量检索未能找到的视频？
2. LLM 重排序能否改善传统检索结果的相关性和排序质量？
3. 三路召回与 Reranker 结合后，是否能够进一步提升搜索效果？
4. 不同方案在响应时间、模型调用成本和系统稳定性方面存在怎样的差异？
5. 在搜索质量、响应速度和调用成本之间，哪种方案更适合 HQH 当前业务需求？

最终根据统一评测数据和实验结果，选择综合表现最优、工程上可落地的搜索架构。

## 二、实验方案设计

本次评测设置四个实验组，分别代表三种主要架构方向及两种不同的 Reranker 实现方式。

### 2.1 实验组 A：三路独立召回 + RRF

**架构组成：**

1. 关键词召回（Keyword Retrieval）。
2. RAG 向量召回（Vector Retrieval）。
3. LLM 主动检索（LLM Retrieval）。
4. RRF 统一排序。

其中，LLM 主动检索由模型理解用户查询，生成适合底层检索的短查询，并通过 `find_videos` 工具进行多轮视频查找，最终选择符合用户需求的视频。

三路召回完成后，将候选结果合并、去重，再通过 RRF 算法进行统一排序。

**主要目的：**

验证 LLM 主动检索能否补充传统检索结果，以及 RRF 能否改善原有固定来源优先级合并方式的排序效果。

### 2.2 实验组 B：关键词 + RAG 召回 + LLM Reranker

**架构组成：**

1. 关键词召回。
2. RAG 向量召回。
3. 候选结果合并、去重。
4. LLM Reranker 重排序。

该方案不设置独立的 LLM 主动检索路径。

关键词和 RAG 负责产生候选视频，LLM Reranker 根据用户原始查询以及候选视频的标题、简介、品牌、型号和标签等信息，判断候选视频的相关程度并重新排序。

**主要目的：**

验证 LLM 重排序能否改善传统双路检索的准确率和排序质量，并评估不引入 LLM 主动检索时的性能与成本表现。

### 2.3 实验组 C1：三路独立召回 + LLM Reranker

**架构组成：**

1. 关键词召回。
2. RAG 向量召回。
3. LLM 主动检索。
4. 候选结果合并、去重。
5. LLM Reranker 重排序。

该方案保留 LLM 主动检索能力，同时增加统一的 LLM 重排序环节。

**主要目的：**

验证 LLM 主动检索与 LLM 重排序能否形成互补，进一步提升候选覆盖率和最终排序质量。

### 2.4 实验组 C2：三路独立召回 + 专用 Reranker

**架构组成：**

1. 关键词召回。
2. RAG 向量召回。
3. LLM 主动检索。
4. 候选结果合并、去重。
5. 专用 Reranker 重排序。

与 C1 的区别在于，最终排序环节不使用通用 LLM，而使用专门的相关性重排序模型。

**主要目的：**

验证专用 Reranker 在相关性判断、响应时间和调用成本方面的表现，判断其是否适合作为 HQH 后续的排序组件。

### 2.5 实验组汇总

| 实验组 | 关键词 | RAG | LLM 主动检索 | 重排序方式 |
|---|---|---|---|---|
| A | ✓ | ✓ | ✓ | RRF |
| B | ✓ | ✓ | — | LLM Reranker |
| C1 | ✓ | ✓ | ✓ | LLM Reranker |
| C2 | ✓ | ✓ | ✓ | 专用 Reranker |

说明：

- 本次正式评测共设置四个实验配置。
- 原有关键词 + RAG 混合检索方案已进行过实际测试，存在向量召回阈值不合理的问题，因此不再设置独立 D 实验组重复测试。
- 原方案的历史测试情况作为本次架构升级的背景依据，不纳入本轮综合评分。

## 三、评测数据集构建

### 3.1 数据集规模

第一轮评测计划建立包含 120 条查询的初始数据集，另设置 10～15 条无匹配结果的压力测试查询。

| 数据类型 | 数量 | 用途 |
|---|---:|---|
| 精确关键词查询 | 30 | 验证精确匹配能力 |
| 自然语言查询 | 30 | 验证自然语言理解能力 |
| 语义表达差异查询 | 30 | 验证语义检索能力 |
| 复杂意图查询 | 30 | 验证查询改写和多轮检索能力 |
| 无匹配压力测试 | 10～15 | 验证无相关结果时的处理能力 |

以上数量为第一轮评测计划，后续可根据实际视频数量和用户查询记录调整。

### 3.2 查询类型定义

**（1）精确关键词查询**

用户直接使用视频中的品牌、型号、功能名称或专业术语进行搜索。

示例：

- 南方 CORS 账号设置
- 某型号手簿蓝牙连接
- GNSS 接收机参数配置

主要测试关键词检索的有效性。

**（2）自然语言查询**

用户使用日常语言描述具体需求，而不是直接输入视频标题或专业术语。

示例：

- 手簿怎么连接网络 RTK？
- 仪器连接不上基站怎么办？
- 如何设置测量参数？

主要测试系统对自然语言表达的处理能力。

**（3）语义表达差异查询**

用户的表达与视频标题、简介中的用词存在明显差异，但实际意图相近。

示例：

- 如何让仪器获取差分数据？
- 怎么让设备正常接收定位信息？
- 手簿如何完成网络连接？

主要测试向量检索和查询改写能力。

**（4）复杂意图查询**

用户通过较长的自然语言描述多个条件或操作需求。

示例：

- 新买的手簿如何完成首次网络配置？
- 某型号设备如何连接网络并完成账号设置？
- 仪器更换设备后应该怎样重新配置参数？

主要测试 LLM 对用户意图的理解、查询拆解和多轮检索能力。

**（5）无匹配结果查询**

查询内容涉及知识库中不存在的视频主题或功能。

示例：

- 如何使用知识库中未收录型号的特殊功能？
- 如何完成与现有视频无关的其他设备操作？

主要测试系统是否会错误返回无关视频。

### 3.3 数据来源

评测查询优先从真实业务数据中获取，主要来源包括：

1. 小程序历史搜索记录。
2. 用户在播放页提出的视频相关问题。
3. 项目测试人员模拟真实使用场景提出的查询。
4. 根据已上架视频的标题、品牌、型号、简介和标签构造的补充查询。

真实用户查询应优先保留原始表达，避免在收集阶段过度规范化，以免失去评估自然语言检索能力的意义。

如涉及用户隐私，应对查询数据进行必要的脱敏处理。

### 3.4 数据集划分

将 120 条有匹配结果的查询划分为：

| 数据集 | 数量 | 用途 |
|---|---:|---|
| 开发集 | 30 | 调整参数、Prompt 和过滤规则 |
| 测试集 | 90 | 最终架构对比和综合评价 |

划分时保证四类查询在开发集和测试集中均有合理分布。

无匹配压力测试集独立保存，不参与普通 Recall@8 和 NDCG@8 的计算。

测试集在各实验组参数确定后使用，不得根据测试结果反复修改 Prompt、阈值或排序规则。

## 四、相关性标注规范

### 4.1 标注目的

为了客观评价搜索结果，需要为每条查询建立对应的相关视频集合，并标注视频与查询之间的相关程度。

相关性标注是 Recall@8、Precision@Returned 和 NDCG@8 的统一计算依据。

### 4.2 相关性等级

采用四级相关性标注：

| 等级 | 名称 | 判断标准 |
|---:|---|---|
| 3 | 高度相关 | 视频能够直接解决用户提出的问题 |
| 2 | 相关 | 视频涉及相关操作或知识，能够提供有效帮助 |
| 1 | 弱相关 | 视频涉及相同设备或主题，但不能有效解决用户问题 |
| 0 | 不相关 | 视频与用户需求没有实质关联 |

例如，用户查询为：

“南方手簿如何配置 CORS 账号？”

对应视频：

| 视频 | 相关性等级 | 标注理由 |
|---|---:|---|
| 南方手簿 CORS 账号设置 | 3 | 直接解决账号配置问题 |
| 南方手簿网络 RTK 连接 | 2 | 与 CORS 连接操作密切相关 |
| 南方手簿蓝牙配对 | 1 | 设备相同，但操作任务不同 |
| 南方仪器固件升级 | 0 | 与查询需求无关 |

### 4.3 二值相关性判定规则

为了统一 Recall 和 Precision 的计算口径，明确规定：

**相关性等级为 2 或 3 的视频，才计入有效相关视频集合。**

即：

| 相关性等级 | 是否计入 Recall | 是否计入 Precision | 是否计入 NDCG |
|---:|---|---|---|
| 3 | 是 | 是 | 是 |
| 2 | 是 | 是 | 是 |
| 1 | 否 | 否 | 是 |
| 0 | 否 | 否 | 是 |

对于二值检索指标，相关视频集合定义为：

\[
Relevant(q)=\{d\mid rel(q,d)\geq 2\}
\]

其中：

- \(q\)：用户查询。
- \(d\)：视频。
- \(rel(q,d)\)：人工标注的相关性等级。

因此，1 分和 0 分的视频均不视为有效相关结果。

这样可以避免仅仅因为视频属于相同品牌、型号或主题，就将不能解决用户实际问题的视频计算为有效命中。

NDCG 则继续采用 0、1、2、3 四级评分，以保留不同相关程度之间的排序差异。

### 4.4 标注方式

建议采用以下流程：

1. 每条查询由两名标注人员独立判断。
2. 对不同方案召回结果进行汇总，建立候选视频并集。
3. 对候选并集中的视频进行相关性标注。
4. 对分歧较大的标注结果进行复核。
5. 必要时根据视频标题、简介、转写内容和实际视频内容补充检查，避免遗漏相关视频。
6. 最终形成统一的查询—视频相关性标注表。

不能只标注某一个实验组返回的视频，否则其他实验组可能召回了正确视频，却无法获得相应的相关性评价。

**特别注意：** 仅使用四个实验组候选结果的并集，仍然可能遗漏所有实验组都没有召回的真正相关视频。因此，应结合视频知识库的标题、简介、品牌、型号、标签和其他可用内容进行补充检索及人工检查，尽可能建立完整的相关视频集合。

如果无法确认相关视频集合完整，应在评测报告中说明这一局限，避免将可能偏高的 Recall 结果解释为真实的完整召回率。

建议数据结构：

```json
{
  "query_id": "Q001",
  "query": "南方手簿如何配置 CORS 账号？",
  "relevance": {
    "video_001": 3,
    "video_002": 2,
    "video_003": 1,
    "video_004": 0
  }
}
```

其中，`video_001` 等 ID 为示意数据。

## 五、实验控制条件

为保证四个实验组的对比公平，需要尽可能统一实验环境和基础检索条件。

### 5.1 统一条件

| 控制项目 | 统一要求 |
|---|---|
| 视频知识库 | 使用同一份已发布视频快照 |
| 视频状态 | 仅包含已上架视频 |
| 搜索文本 | 使用同一版本 `searchBlob` |
| Embedding 模型 | 使用同一模型及版本 |
| 向量索引 | 使用同一份索引快照 |
| 关键词算法 | 使用同一版本 |
| 同义词表 | 使用同一版本 |
| 用户查询 | 使用同一批测试查询 |
| 最终返回数量 | 最多 8 条 |
| 模型版本 | 固定各实验组使用的模型版本 |
| 缓存策略 | 各实验组采用相同的缓存规则 |

### 5.2 RAG 召回规则

为避免原有固定阈值对实验结果产生不合理影响，本次评测统一采用 Top-K 候选召回作为向量检索的初始策略。

具体要求：

1. 使用相同 Embedding 模型计算查询向量。
2. 从符合索引状态及内容版本要求的向量中进行相似度排序。
3. 初始取相似度最高的 8 条作为 RAG 候选。
4. 不再直接使用原有 0.678 作为固定召回门槛。
5. 保留原始余弦相似度和排序信息，供后续分析使用。

如果向量索引覆盖不完整，必须记录该次召回的覆盖状态，不能将不完整索引下的结果直接当作完整知识库的搜索结果。

本次实验主要比较搜索架构，不单独开展 Embedding 模型选型实验。

### 5.3 候选池控制

为避免候选数量差异过大影响重排序的计算成本，设置统一的候选池上限。

建议：

- 关键词召回：最多保留 8 条候选。
- RAG 召回：最多保留 8 条候选。
- LLM 主动检索：最多调用 `find_videos` 3 次，每次最多返回 8 条卡片。
- 三路结果合并后：按视频 ID 去重，候选池最多保留 24 条。
- 最终展示：最多返回 8 条视频。

方案 B 不包含 LLM 主动检索，其候选池由关键词和 RAG 两路组成。

所有候选截断和排序规则应在正式测试前固定，并记录实际候选数量。

### 5.4 LLM 主动检索限制

方案 A、C1 和 C2 使用相同的 LLM 主动检索配置：

- 使用相同模型版本。
- 使用相同 System Prompt。
- 每轮最多调用 3 次 `find_videos`。
- 每次工具调用最多返回 8 条视频卡片。
- 最终最多选择 8 个视频 ID。
- 设置统一的执行时间预算。
- 记录模型实际生成的查询、工具调用次数及最终选择结果。

工具召回候选和模型最终选择结果必须分开记录，不能将工具返回的全部候选直接视为 LLM 最终召回结果。

### 5.5 Reranker 限制

方案 B、C1 使用相同的 LLM Reranker 模型、Prompt 和输入字段。

方案 C2 使用选定的专用 Reranker 模型。

所有 Reranker 仅接收候选视频卡片，不允许直接访问完整数据库或任意视频数据。

建议统一使用：

- 用户原始查询；
- 视频 ID；
- 视频标题；
- 品牌和型号；
- 视频标签；
- 视频简介或搜索摘要。

Reranker 应输出候选 ID 和相关性排序结果，最终 ID 必须来自本轮候选池。

如果采用相关性阈值过滤，阈值应仅在开发集上确定，并在正式测试前固定。不能根据测试集结果临时调整。

## 六、评价指标与计算方法

本次评测采用检索效果、系统性能、调用成本和稳定性四个维度。

### 6.1 检索效果指标

检索效果是本次架构选型最重要的评价维度。

本次采用三个主要指标：

- Recall@8：召回率。
- Precision@Returned：实际返回结果准确率。
- NDCG@8：排序质量。

其中，Recall 和 Precision 使用统一的二值相关性定义，即相关性等级为 2 或 3 的视频才计为有效相关结果。

NDCG 继续采用四级相关性评分。

**（1）Recall@8：召回率**

衡量最终最多 8 条结果中，系统找到了多少真正相关的视频。

\[
Recall@8(q)=
\frac{|Relevant(q)\cap Top8(q)|}{|Relevant(q)|}
\]

其中：

- \(Relevant(q)\)：查询 \(q\) 对应的全部有效相关视频集合，即人工标注等级为 2 或 3 的视频。
- \(Top8(q)\)：系统针对查询 \(q\) 最终返回的最多 8 条视频。

例如，某条查询共有 5 条有效相关视频，系统前 8 条找到了其中 4 条：

\[
Recall@8=\frac{4}{5}=0.8
\]

Recall@8 越高，说明系统遗漏的相关视频越少。

**（2）Precision@Returned：实际返回结果准确率**

衡量系统实际返回的视频中，有多少是真正相关的视频。

\[
Precision@Returned(q)=
\frac{|Relevant(q)\cap Returned(q)|}{|Returned(q)|}
\]

其中：

- \(Relevant(q)\)：查询对应的全部有效相关视频集合。
- \(Returned(q)\)：系统实际返回的视频集合，最多包含 8 条。

例如：

| 搜索情况 | 正确视频数 | 实际返回数 | Precision@Returned |
|---|---:|---:|---:|
| 只返回 1 条正确视频 | 1 | 1 | 100% |
| 返回 3 条，其中 2 条正确 | 2 | 3 | 66.7% |
| 返回 8 条，其中 5 条正确 | 5 | 8 | 62.5% |
| 返回 8 条，其中 1 条正确 | 1 | 8 | 12.5% |

与固定分母的 Precision@8 不同，Precision@Returned 使用实际返回数量作为分母，可以更合理地评价 HQH 中相关视频数量较少的查询。

**空结果处理规则：**

- 对于存在有效相关视频的查询，如果系统没有返回任何视频，则该次 Precision@Returned 记为 0，防止系统通过不返回结果获得虚高准确率。
- 对于知识库中确实不存在有效相关视频的查询，不纳入普通 Precision 和 Recall 的宏平均计算，而是进入无匹配压力测试，单独评价正确空结果率和误召回率。

**宏平均计算：**

最终采用宏平均计算测试集整体 Precision：

\[
MacroPrecision=
\frac{1}{N}\sum_{q=1}^{N}Precision@Returned(q)
\]

其中，\(N\) 为存在有效相关视频的测试查询数量。

每条查询具有相同权重，避免相关视频数量较多的查询对整体结果产生过大影响。

Recall@8 同样采用宏平均：

\[
MacroRecall@8=
\frac{1}{N}\sum_{q=1}^{N}Recall@8(q)
\]

这样可以反映不同查询场景下的平均检索能力。

**（3）NDCG@8：排序质量**

NDCG 用于评价相关视频是否被合理地排在前面。

采用四级相关性等级：

- 3：高度相关；
- 2：相关；
- 1：弱相关；
- 0：不相关。

计算公式：

\[
DCG@8=\sum_{i=1}^{8}
\frac{2^{rel_i}-1}{\log_2(i+1)}
\]

\[
NDCG@8=\frac{DCG@8}{IDCG@8}
\]

其中：

- \(rel_i\)：排名第 i 位视频的人工相关性等级。
- \(IDCG@8\)：理想排序情况下的 DCG@8。

NDCG@8 越高，说明真正相关的视频越靠前，同时高度相关视频获得了更好的排名。

对于没有有效相关视频的查询，NDCG 不纳入普通测试集宏平均，相关结果单独分析。

### 6.2 辅助指标：Hit@1

考虑到 HQH 的用户通常希望快速找到能够直接解决问题的视频，额外记录 Hit@1。

Hit@1 用于判断搜索结果的第一条视频是否真正相关。

\[
Hit@1(q)=
\begin{cases}
1,&rel(q,d_1)\geq2\\
0,&\text{其他情况}
\end{cases}
\]

其中，\(d_1\) 为系统返回的第一条视频。

最终计算：

\[
Hit@1=
\frac{\text{第一条结果相关的查询数量}}
{\text{存在有效相关视频的查询总数}}
\]

Hit@1 越高，说明用户在搜索后第一时间看到有效视频的概率越高。

该指标作为辅助观察指标，不纳入综合评分权重。

### 6.3 系统性能指标

第一轮只保留两个主要指标。

**（1）平均响应时间**

衡量一次完整搜索请求从发起到返回最终结果所需要的平均时间。

\[
T_{avg}=\frac{1}{N}\sum_{i=1}^{N}T_i
\]

其中：

- \(N\)：有效搜索请求数量。
- \(T_i\)：第 i 次完整搜索请求的响应时间。

统计时应包含：

- 关键词检索；
- Embedding 调用；
- LLM 主动检索（适用时）；
- Reranker 调用（适用时）；
- 候选合并及排序；
- 其他必要的数据处理。

并行执行的检索路径应按照实际请求总耗时统计，不能简单将各路径耗时相加。

**（2）P95 响应时间**

衡量 95% 搜索请求能够在多长时间内完成。

将所有有效请求耗时按从小到大排列，使用统一的百分位数计算方法得到 P95。

P95 越低，说明大部分用户能够获得更稳定的响应速度。

### 6.4 调用成本指标

本次只将平均单次搜索成本作为主要成本指标。

\[
C_{avg}=\frac{\sum_{i=1}^{N}C_i}{N}
\]

其中：

- \(C_i\)：第 i 次完整搜索请求产生的实际调用成本。
- \(N\)：搜索请求数量。

成本统计主要包括：

| 成本项目 | 统计要求 |
|---|---|
| Embedding | 统计实际调用费用 |
| LLM 主动检索 | 统计输入、输出 Token 对应费用 |
| LLM Reranker | 统计模型调用费用 |
| 专用 Reranker | 统计实际 API 或服务调用费用 |
| 关键词检索 | 不产生模型 API 调用费用 |
| RRF | 不产生额外模型调用费用 |

所有费用统一换算为人民币，使用实际模型单价和调用量计算。

对于不同模型的计价方式，应按照对应服务商的实际计费规则进行换算。

云函数计算、数据库读取等基础设施成本第一轮暂不纳入综合评分，但如果某个方案显著增加相关资源消耗，应单独记录。

### 6.5 稳定性指标

稳定性只保留两个辅助指标：

**（1）失败率**

\[
FailureRate=\frac{N_{failed}}{N_{total}}\times100\%
\]

其中，失败请求包括未能正常完成搜索并返回有效业务响应的请求。

**（2）超时率**

\[
TimeoutRate=\frac{N_{timeout}}{N_{total}}\times100\%
\]

其中，超时请求指完整搜索链路超过统一设定的执行时间限制。

失败率和超时率作为辅助指标，同时纳入最终稳定性评价。

### 6.6 暂不纳入第一轮评测的指标

以下指标暂时不作为主要评价项目：

- CPU 使用率；
- 内存使用率；
- 并发吞吐量；
- P50 响应时间；
- 数据库读取次数；
- 单独的模型 Token 数综合评分。

其中，模型 Token 消耗仍然作为成本分析的辅助记录项。

如果未来需要评估大规模并发能力，再单独开展压力测试。

## 七、实验执行流程

### 7.1 第一阶段：数据准备

1. 获取同一版本的已发布视频知识库。
2. 确认视频搜索文本和向量索引的一致性。
3. 收集并整理 120 条有匹配结果的测试查询。
4. 额外准备 10～15 条无匹配压力测试查询。
5. 完成开发集和测试集划分。
6. 建立统一的相关性标注数据。

### 7.2 第二阶段：实验配置实现

分别准备：

- A：三路召回 + RRF。
- B：关键词 + RAG + LLM Reranker。
- C1：三路召回 + LLM Reranker。
- C2：三路召回 + 专用 Reranker。

优先复用现有 `search` 云函数、`find_videos` 工具和 `videoSearchLane` 中已经实现的能力。

评测代码应与生产搜索逻辑分离，避免将实验配置和测试逻辑直接耦合进生产云函数。

### 7.3 第三阶段：参数调整

使用开发集完成：

- RAG 候选数量和相关性过滤规则调整；
- LLM 主动检索 Prompt 调整；
- RRF 参数调整；
- LLM Reranker Prompt 调整；
- 专用 Reranker 模型选择；
- 必要的相关性阈值调整。

完成后固定模型版本、Prompt、参数和候选截断规则。

### 7.4 第四阶段：正式测试

使用 90 条测试查询运行四个实验组。

建议：

1. 每个实验组使用相同的查询集合。
2. LLM 相关实验至少重复运行 3 次。
3. 记录各次搜索结果及实际执行日志。
4. 统计平均响应时间和 P95。
5. 记录模型调用次数、Token 消耗和实际调用费用。
6. 对搜索结果计算 Recall@8、Precision@Returned 和 NDCG@8。
7. 同时记录 Hit@1 作为辅助指标。

为了保证实验可重复，应记录模型版本、索引版本、实验配置版本及测试时间。

### 7.5 第五阶段：无匹配压力测试

对独立的无匹配查询进行测试，重点观察：

- 是否错误返回大量无关视频；
- 是否能够正确返回空结果；
- 是否存在模型编造视频 ID 的情况；
- 是否因为 LLM 强行检索而产生误召回。

该部分不纳入普通 Recall@8、Precision@Returned 和 NDCG@8 计算，单独报告：

- **正确空结果率**：知识库确实不存在有效相关视频时，系统正确返回空结果的比例。
- **误召回率**：知识库不存在有效相关视频时，系统仍返回视频的比例。

### 7.6 第六阶段：结果分析

分别统计：

- 四个实验组的整体效果；
- 不同查询类型下的效果；
- 响应时间和调用成本；
- 超时和失败情况；
- 各召回路径对最终结果的贡献。

最终形成对比报告和架构选型建议。

## 八、综合评价与最终选型

### 8.1 指标权重

采用质量优先、性能与成本兼顾的评价方式。

| 评价维度 | 指标 | 权重 |
|---|---|---:|
| 检索效果 | Recall@8 | 20% |
| 检索效果 | Precision@Returned | 20% |
| 检索效果 | NDCG@8 | 25% |
| 系统性能 | 平均响应时间 | 7.5% |
| 系统性能 | P95 响应时间 | 7.5% |
| 调用成本 | 平均单次搜索成本 | 15% |
| 稳定性 | 失败率、超时率 | 5% |
| **合计** | | **100%** |

Hit@1 作为辅助指标，不纳入综合评分。

### 8.2 指标标准化

不同指标具有不同量纲，需要先转换为统一的 0～100 分。

对于越高越好的指标，可采用：

\[
Score_{higher}=
100\times\frac{x-x_{min}}{x_{max}-x_{min}}
\]

对于越低越好的指标，可采用：

\[
Score_{lower}=
100\times\frac{x_{max}-x}{x_{max}-x_{min}}
\]

其中：

- \(x\)：当前方案的实际指标值。
- \(x_{min}\)、\(x_{max}\)：参与比较方案的最小值和最大值。

当所有方案的某个指标相同时，该项视为没有区分能力，不应通过除以零计算得分。

### 8.3 综合得分

\[
Score=
0.20R+
0.20P+
0.25N+
0.075L_1+
0.075L_2+
0.15C+
0.05S
\]

其中：

- \(R\)：Recall@8 标准化得分。
- \(P\)：Precision@Returned 标准化得分。
- \(N\)：NDCG@8 标准化得分。
- \(L_1\)：平均响应时间得分。
- \(L_2\)：P95 响应时间得分。
- \(C\)：平均单次搜索成本得分。
- \(S\)：稳定性得分。

对于稳定性得分，结合失败率和超时率进行评价。

上述权重为第一轮建议配置，可在正式实验前确定，不应根据测试结果临时调整。

### 8.4 质量门槛

除综合评分外，还需要设置最低质量和性能要求，避免出现某个方案通过牺牲搜索效果换取低成本，却最终获得较高综合评分的情况。

第一轮建议暂定：

| 指标 | 初始目标 |
|---|---:|
| Recall@8 | ≥ 0.80 |
| Precision@Returned | ≥ 0.60 |
| NDCG@8 | ≥ 0.75 |
| P95 响应时间 | ≤ 5 秒 |
| 超时率 | ≤ 1% |

以上为待验证的初始验收目标，不代表当前系统已经达到这些指标，也不是通用行业标准。

其中，Precision@Returned 的 0.60 门槛针对存在有效相关视频的查询集合计算的宏平均值，而不是要求每条查询单独达到 0.60。

如果所有方案均未达到某项门槛，应分析原因并调整业务要求或方案，而不是直接选择相对得分最高的方案。

### 8.5 最终选型原则

最终选择应遵循：

1. 优先满足基本检索质量要求。
2. 在质量达标的方案中比较综合评分。
3. 结合 P95 延迟和实际调用成本判断工程可行性。
4. 分析不同查询类型下的表现，避免总体平均值掩盖局部问题。
5. 对综合评分接近的方案，优先考虑实现复杂度更低、维护成本更小的方案。
6. 对权重进行敏感性分析，判断最终选择是否稳定。

不能仅根据某一项指标的最高值决定最终架构。

本次评测完成后，预期形成以下成果：

3. 四个搜索架构实验配置及对应实现。
4. 一套自动化搜索评测与指标计算工具。

6. 一份基于实验数据的 HQH 搜索架构最终选型建议。

最终通过实验结果判断：

- LLM 主动检索是否值得保留；
- LLM 重排序是否能够有效改善检索质量；
- 专用 Reranker 是否具有实际应用价值；
- 三路召回与重排序结合是否优于双路召回与重排序。

## 十一、实施原则与注意事项

1. 本次评测以真实搜索需求为基础，优先使用实际用户查询。
2. 四个实验组必须使用同一份知识库快照和统一的基础检索配置。
3. 开发集用于参数调整，测试集仅用于最终评价。
4. 不得根据测试集结果反复修改 Prompt、模型配置或排序规则。
5. 所有模型调用费用按照实际调用量和实际计价规则统计。
6. LLM 工具召回候选与最终筛选结果必须区分。
7. 无匹配结果查询应独立评估，不能强行要求系统返回 8 条视频。
8. 相关视频集合应尽可能完整，不能仅依赖各实验组召回结果的并集。
9. Recall 和 Precision 统一采用相关性等级 2、3 作为有效相关标准；NDCG 使用 0～3 级评分。
10. Precision@Returned 对存在有效相关视频但返回空结果的查询记为 0。
11. 评测日志应记录足够的信息，以便复现和分析实验结果。
12. 不预设任何方案一定优于其他方案，不虚构实验结果。
13. 最终架构选择以检索质量、响应性能、调用成本和工程可维护性为依据。

**本次评测的核心目标不是证明某一种搜索架构更先进，而是通过统一、可复现的实验，选择最适合 HQH 当前业务需求和工程条件的视频搜索方案。**
