# 版本号与更新说明

包内版本写在 `miniprogram/data/appRelease.js`，关于页和运营「版本与日志」都读这份数据。微信开发者工具上传时填写的版本号必须与其中的 `version` 相同。

## 原则

- **默认升小版本**：修缺陷、文案、样式、小体验，只动修订号。
- **有用户能感知的新能力**，再升次版本。
- **正式上线（微信审核通过并发布）之前，禁止 `1.0.0` 及任何 `1.x`。** 开发、联调、体验版一律停在 `0.x.y`。
- `1.0.0` 只用于第一次正式上线。之后的大改再升主版本（`2.0.0` 等）。

## 怎么升

版本形如 `主.次.修订`，当前阶段主版本固定为 `0`。

| 改动 | 升哪一位 | 例子 |
| --- | --- | --- |
| 热修、文案、样式、裁剪/换链一类修复 | 修订号 `z + 1` | `0.1.0` → `0.1.1` |
| 用户能用到的新功能（新页、新流程、商城可买等） | 次版本 `y + 1`，修订号归零 | `0.1.1` → `0.2.0` |
| 第一次正式上线 | 主版本到 `1.0.0` | 仅审核通过并发布时 |
| 正式上线之后的破坏性大改 | 主版本 `+ 1` | 很少用 |

不要为「感觉是个大功能」在体验阶段跳到 `1.0.0`。体验版可以反复传 `0.1.x` / `0.2.0`。

## 更新日志怎么写

每次升 `version`，在 `releases` **数组最前面**加一条，字段：

- `version`：与文件顶层 `version` 相同
- `date`：当天 `YYYY-MM-DD`
- `user`：用户关于页能看到的句子；只写他们能感知的变化，不写云函数名、分支名
- `internal`：仅运营可见；可写入库、裁剪、换链、占位范围等

规则：

- 用户无感知的热修：`user` 可空，只写 `internal`。该条不会出现在用户关于页。
- 首发、次版本：`user` 至少一条，用短句，避免堆砌实现细节。
- 不必回溯没发过的历史版本；只记录真正上传过的包。

## 发版时核对

1. 改 `appRelease.js` 的 `version` 并追加 `releases` 条目。
2. 上传体验版 / 正式版时，工具里的版本号与 `version` 填成一样。
3. 看一眼关于页：用户路径没有 `internal`；运营路径有。
4. 单测 `miniprogram/utils/appRelease.test.js` 会拒绝 `1.x`（正式上线启用 `1.0.0` 时，先改掉那条断言，再改数据）。

分支约定见 `docs/branching.md`：日常改动在 `dev`，上传对准已验证的 `main`。
