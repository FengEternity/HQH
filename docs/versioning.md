# 版本号与更新说明

包内版本写在 `miniprogram/data/appRelease.js`，关于页和运营「版本与日志」都读这份数据。微信开发者工具上传时填写的版本号必须与其中的 `version` 相同。

## 什么时候改

**日常改代码、修缺陷、合分支，一律不要动版本号，也不要改 `releases`。**

只有负责人明确说「更新版本 / 发体验版 / 正式上线」时，才改 `appRelease.js`。没这句话就保持当前 `0.1.0`（或当时已发布的号）。

同一版号可以对应很多提交；关于页记录的是**发过的包**，不是每一笔 git 提交。

## 升哪一位（仅在被要求发版时）

版本形如 `主.次.修订`。正式上线（微信审核通过并发布）之前，主版本固定为 `0`，**禁止 `1.0.0` 及任何 `1.x`。** `1.0.0` 只用于第一次正式上线。

发版时默认升小版本：

| 这一次要发出去的内容 | 升哪一位 | 例子 |
| --- | --- | --- |
| 热修、文案、样式、体验修补 | 修订号 `z + 1` | `0.1.0` → `0.1.1` |
| 用户能用到的新功能 | 次版本 `y + 1`，修订号归零 | `0.1.1` → `0.2.0` |
| 第一次正式上线 | `1.0.0` | 仅审核通过并发布时 |
| 正式上线之后的破坏性大改 | 主版本 `+ 1` | 很少用 |

不要因为仓库里刚合了大功能就自动升号；等明确要求发版时，再按上表选一位。

## 被要求发版时怎么改日志

1. 改顶层 `version`。
2. 在 `releases` **数组最前面**加一条：`version` 与顶层相同，`date` 为当天 `YYYY-MM-DD`。
3. `user`：用户关于页可见；只写他们能感知的变化。无感知的热修可留空（该条不会出现在用户关于页）。
4. `internal`：仅运营可见。
5. 上传体验版 / 正式版时，工具里的版本号与 `version` 填成一样。
6. 单测会拒绝 `1.x`；真要发 `1.0.0` 时先改掉 `appRelease.test.js` 里那条断言。

不必为没上传过的提交补历史版本。

分支约定见 `docs/branching.md`。
